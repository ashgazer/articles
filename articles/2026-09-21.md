Spotting leaked vocabulary
- Ask "whose word is this?" for every noun/verb in a method or param name — if it names a different system's concept (Auth, persistence, a shared library) rather than this domain's own concept, that's a signal.
- A name that matches the underlying data column/table (auth_user_id) is a clue it was named after the infrastructure, not the business concept.

Finding the domain's actual word (don't invent one)
- Grep the domain for existing classes/ports naming the concept (CustomerRepository, CustomerDetailsDTO, *CustomerException) before choosing a word — reuse what's already established rather than picking a "nicer-sounding" synonym.
- If nothing exists, that's worth flagging explicitly ("no precedent for this, first use") rather than presenting it as if it matches a convention.

Checking for name collisions before reusing a word
- If the domain already uses that word for something with a different shape or meaning (e.g. customerId as an internal int), don't reuse it for a different value (an external string auth id) — collision on name but not on meaning is worse than the original leak.
- Where that happens, keep the disambiguating suffix on the low-level parameter even while the method-level verb moves to domain language.

Don't rename what you don't own
- Only rename the class's own public surface. Leave a dependency's method name alone if it's fixed by a shared interface/contract (OwnableInterface::getOwnerAuthId()) — that's a different blast radius and a different owner's decision.

Placement follows the architecture doc, not intuition
- Check the relevant ADR for a rule that governs where something must live (ADR 0009: does another domain need to catch this exception? If yes → the marked cross-domain namespace; if no → keep it private).
- Two similarly-named things can legitimately live in different places for different reasons — don't consolidate on name-similarity alone without checking whether they serve the same audience/contract.

Verify precedent, don't assume it
- Before saying "this matches the convention," grep for other real examples in the codebase. If there are none, say so — it changes whether you're following a pattern or setting one.
- Confirm nesting/structuring conventions (e.g. Exceptions\ subfolders) the same way — check how pervasive it actually is before adopting it.

Propagate the rename
- Update every place the old name appears — tests, local variables, docblocks — so nothing readable still uses the discarded vocabulary.
